## 1. [P1] 实例入口已拒绝时仍分配 IP 桶，满容量回收阻塞全局索引锁

定位：`internal/http/api_rate_limit_middleware.go:21`，关联 `internal/ratelimit/ratelimit.go:98`、`:105`、`:146`。

新的入口顺序先执行 IP 桶检查，再检查实例总量。IP 检查会创建新桶；当索引达到 100,000 条容量上限时，`ensureCapacityLocked` 在所有请求共用的 `Limiter.mu` 内扫描全部条目寻找过期项，无过期项时又遍历一次寻找最老记录。

因此，在大量不同来源请求、实例总量已经耗尽时，后续新来源仍能绕过实例的廉价拒绝路径，持续触发 O(N) 分配/回收工作。这些请求甚至无需有效 API Key。管理员和会话的固定限流也共用这个索引锁，业务流量会阻塞它们。旧链路在实例入口已拒绝时直接返回，不会再创建来源桶；这次调整扩大了旧回收算法的开销暴露范围。

独立容量基准：100,000 个来源桶＋一个已耗尽的实例桶，每次用新来源请求，所有桶均未过期：

| 顺序 | 每次拒绝成本 |
| --- | ---: |
| 实例入口先拒绝 | 173.5 ns/op |
| 当前 IP 先分配、再由实例拒绝 | 21,332,378 ns/op，约 21.3 ms |

基准使用固定时钟排除令牌补充差异；数据是本机算法成本，不是部署吞吐承诺。建议在实例已饱和时提供不分配 IP 桶的拒绝路径，同时把容量维护改为有界操作，避免在全局锁内遍历整个索引。应保留“IP 拒绝不消耗实例令牌”的行为，通过独立的准入检查/明确的桶存储职责解决，而不是继续在处理器添加特殊分支。

## 2. [P2] 缓存版本、编辑基线和冲突状态分别维护，表单会错误地变为干净状态

定位：`web/src/features/admin/components/APIRateLimitSettingsPanel.tsx:54`、`:59`，关联 `:117`、`:239`、`:255`。

`settings.data`、`editor.form/baseline/revision` 和 `conflict` 是分别推进的状态。接收新服务器配置时，Effect 因草稿非空保留旧 editor，但只依赖 `[data]`，之后草稿回到旧 baseline 并不会重新协调服务器快照。

确定性复现：初始版本 1 的邮件速率为 2 → 修改为 80 → 另一管理员把服务器更新为版本 2、速率 30，后台刷新接收该值但保留草稿 → 当前用户把输入改回 2。此时页面显示 2、`dirty=false`，保存与撤销均被禁用，最新更新时间却来自版本 2。页面既未显示当前配置 30，也不能保存用户输入的 2。

另一个探针显示：发生 409 后，用户恢复旧 baseline，再收到新快照，editor 会更新而独立 conflict 标志仍保留。它不是独立的权限问题，但说明“采用新快照”并没有统一处理编辑、基线和冲突状态。

建议将“服务器快照、可选草稿、草稿基准版本”统一为明确的编辑模型，由接收快照、编辑、撤销、重载和保存成功这些操作协调状态。当没有未保存差异时展示最新快照；有差异时保持版本绑定，并继续要求显式解决冲突。不要仅增加 Effect 条件，或无条件清除冲突标志。

## 3. [P2] 固定 10 分钟回收与新增低速率配置不兼容，空闲会提前补满整桶

定位：`internal/ratelimit/ratelimit.go:105`、`:106`，关联 `:190`；新增配置范围位于 `internal/apiratelimit/policy.go:12`。

现在允许 0.001/s 和很大的 burst，但桶仍只依据固定空闲 TTL 删除。记录回收后通过 `rate.NewLimiter` 重建会获得完整 burst，即使按照配置速率尚不足以补充一个令牌。旧固定规则的补满时间远短于 TTL，新允许的配置使这一假设不再成立。

独立假时钟复现：设置 `rate=0.001/s, burst=100` 并用完 100 个令牌；15 分钟后执行生产所用的空闲回收逻辑，然后再次请求。仅过了 900 秒，应累积 0.9 个令牌，但重建桶立即放行。每隔 15 分钟重复，45 分钟共放行 **400 次**；按一个初始 burst 加自然补充，上界应为 **102 次**。

方案中允许自然回收后新桶取得初始额度，但当前可配置范围使这个行为可以显著改变长期速率，和面板“每秒请求数”的含义冲突。应让安全回收条件覆盖桶实际补充周期，例如只有额度已自然恢复到完整容量且达到空闲时间才可无损丢弃；若内存上限不允许保留长时间欠额，则需明确限制可接受参数组合或设计有界的溢出策略。不能只维持固定 TTL 并依赖文档解释。

## 验证口径修正（非合入阻塞项）

`internal/http/api_rate_limit_load_test.go:55` 设置了 cost=12，并在 `:62` 创建 Key、`:66` 读取 hash 的 cost，但实际 `APIKeyService.Authenticate` 首先按 `key_value` 查询。`CreateFor` 保存了该字段，因此压测请求直接命中索引并返回，不执行 bcrypt 比较。

独立探针把 KeyHash 设置为无效 bcrypt 字符串，保持匹配的 `key_value`，请求仍成功认证。这证明压测中的 `bcrypt_cost=12` 是存储 hash 的属性，不是每请求执行过的成本。当前数据仍可代表该明文索引命中路径，但应修正运维文档、验收报告与 Memory 中可能造成误解的“包含生产 bcrypt 校验成本”表述；若要评估仅存 hash 的历史 Key，应增加明确的独立场景，而非混在现有结果中。
