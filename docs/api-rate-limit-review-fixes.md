| 问题 | 修复与结果 |
| --- | --- |
| P1：满容量入口检查持全局锁扫描桶表 | 用每桶一个节点的有序回收队列替代全表扫描；容量满时只检查一个候选。实例额度先无消费、无分配预检，再按 IP → 实例顺序扣额；饱和时不创建 IP 桶。API 和管理员/会话保护使用两个独立的有界存储。 |

| 压测口径 | 明确测试请求按 `key_value` 索引认证，不执行逐请求 bcrypt 比较。后续结果使用 `authentication_path=key_value_index` 和 `stored_bcrypt_cost=12`；历史测量数值保留，并解释旧 `bcrypt_cost` 字段的实际含义。 |

## 性能与边界

同机 Go 1.25.10、i5-10300H 微基准，表内为每次限流器操作的成本：

| 场景 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 1,000 桶满载后新身份检查 | 53.65 μs | 0.264 μs |
| 100,000 桶满载后新身份检查 | 16.22 ms | 0.306 μs |
| 100,000 桶下实例饱和预检 | — | 0.324 μs，零分配 |
| 并行热 Key | 0.386 μs | 0.294 μs，零分配 |
| 并行 1,024 Key | 0.378 μs | 0.587 μs，零分配 |

满容量比较使用同一基准；旧实现替换欠额桶并放行，新实现保留欠额并拒绝新身份。多 Key 场景增加了维护有序回收索引的成本，换取安全回收及有界容量维护。以上是限流器微基准，不能推导部署的 HTTP 吞吐。

容量维护采用保守准入：队首候选尚未补满时拒绝新身份，不扫描其他桶；API 与固定保护各自默认上限为 100,000 个桶。已有身份继续按令牌规则工作，修改配置不会清空额度或绕过容量限制。运行说明见[运维文档](api-rate-limits.md)。

## 原则、经验和后续

- KISS：用单一编辑模型处理状态转换，用标准堆表达回收顺序，删除全表扫描和分散的冲突状态更新。
- YAGNI：保持固定七项规则及现有单实例计数范围，本轮集中修复已证实的边界。
- SOLID：通用桶不依赖 HTTP 或数据库；API 准入与固定管理保护各自拥有存储；表单模型与请求编排职责明确。
- DRY：复用 `x/time/rate`、现有表单指纹工具及统一的桶键、策略转换、429 响应逻辑。
- 经验：缓存 TTL 不能决定尚欠额度的生命周期；表单的“无修改”必须与最新快照协调。上轮临时探针已不存在，本轮将复现纳入项目测试，并将结果保存到仓库以便跨会话追溯。

下一步可在目标部署上使用实际 IP/Key 分布、CPU 和数据库条件重跑 HTTP 负载测试，评估参数与容量预算。该步骤属于部署性能评估，三个审查问题的修复和本地验证已完成。
