## 性能记录

环境：Linux amd64，Intel Core i5-10300H，8 逻辑 CPU，Go 1.25.10，PostgreSQL 18.6；连接池上限 25。真实 HTTP 请求为 `GET /api/mailboxes`，8 个并发 worker、同一 Key、空邮箱数据。密钥按 `key_value` 索引命中认证，不执行逐请求 bcrypt 比较；存储哈希的 cost 为 12。每个场景持续约 6 秒，客户端故意不退避，以观察拒绝行为。

| 场景 | 成功数 | 429 数 | 异常数 | 成功 RPS | 成功 P95 | 成功 P99 | 池等待 | 限流配置查询 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 默认规则 | 31 | 65,605 | 0 | 5.17 | 521.82 ms | 559.40 ms | 0 | 0 |
| IP、实例、邮件规则提高到 1000/s、burst=1000 | 128 | 80 | 0 | 19.29 | 868.60 ms | 1130.18 ms | 0 | 0 |

默认场景包含初始突发额度，因此短时平均成功 RPS 高于持续速率 2/s。提高阈值沿用已耗尽的桶，过渡期间的 80 次拒绝符合“更新不赠送新桶”的行为。此短时、单 Key 测试不代表最大吞吐或长期稳态容量。

提高阈值后，数据库日志显示同一 API Key 配额更新的行锁等待；连接池本身未等待。索引命中认证、配额更新、使用日志和业务 SQL 都包含在测量内，bcrypt 比较成本不包含在内。历史 JSON 中的 `bcrypt_cost` 字段表示存储哈希的属性；后续压测改用 `stored_bcrypt_cost` 和 `authentication_path` 明确区分。因此不能将配置上限当作吞吐能力，也不能把此结果用于仅存哈希的密钥认证路径。

令牌桶并行微基准：热 Key 347.2 ns/op，1024 Key 场景 304.7 ns/op，均为 0 B/op、0 allocs/op。配置读取不增加每请求 SQL。

## 关键修复与原则应用

- SQLite 先读后写会发生事务锁升级失败；改为带版本条件的空更新先取得写锁，统一 SQLite/PostgreSQL 的并发冲突语义。
- 数据库时间精度可能改变更新时间；使用 `RETURNING` 取得实际持久化结果，保存响应、后续读取与审计时间一致。
- 旧查询可能在保存后覆盖缓存；保存后取消旧查询，查询支持取消信号。退出/切换账号后，旧保存回调不能重建缓存。冲突重载期间锁定表单，避免覆盖期间的新输入。
- 数值解析先限定十进制语法，再校验服务端边界，拒绝隐式十六/二/八进制及截断输入。
- KISS/YAGNI：保留固定七项规则和既有单实例令牌桶，不引入任意规则语言或共享计数服务。
- SOLID：配置策略、事务存储、内存发布、HTTP 编排及表单各自承担明确职责。
- DRY：默认值和边界由后端统一提供；路由目录绑定策略；原生与 YYDS 共用限流/配额编排；公开文档复用同一重试说明。
